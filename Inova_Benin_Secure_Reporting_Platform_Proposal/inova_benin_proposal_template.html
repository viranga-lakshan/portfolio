Answers to Mandatory Screening Questions 1 & 2

Detailed technical responses outlining our real-world implementation of zero-knowledge end-to-end encryption, asymmetric key management, and FIDO2/WebAuthn hardware protection.

QUESTION 1 Describe one project you delivered with end-to-end encryption (zero-knowledge server): your exact role, libraries/protocols used, and key management.

Project: Enterprise Secure Messaging & Incident Reporting Module (Arimac Digital & Ooredoo Telecom Group · Lead Backend Architect: Avishka Meddegoda).

  • Zero-Knowledge Architecture: Built on a client-side hybrid cryptosystem using Libsodium (NaCl / libsodium-wrappers) and the Web Crypto API. The central server operates strictly as an untrusted blind storage relay, completely incapable of reading report payloads, subject lines, or attachments.
  • Cryptographic Protocol: Each report payload is encrypted client-side using authenticated symmetric encryption (AES-256-GCM / ChaCha20-Poly1305) with a unique ephemeral 256-bit symmetric session key. This session key is then encrypted with the public keys of authorized case handlers using X25519 asymmetric key agreement and HKDF (HMAC-based Extract-and-Expand Key Derivation).
  • Key Management & Zero Escrow: Authorized investigators generate their X25519 / Ed25519 keypairs locally within their secure browser/device enclave. Private keys are never transmitted to or stored on the backend; they are encrypted at rest using an Argon2id-derived key from a high-entropy passphrase, stored in IndexedDB/Android KeyStore, and only decrypted in volatile memory upon hardware-key authorization.
  • Public Reference Links: DU Telecom Greenfield Digital Platform (du.ae/personal ↗) and Moolee Marketplace (moolee.mv ↗).
QUESTION 2 What is your hands-on experience with FIDO2/WebAuthn hardware keys? Describe how you would protect an admin dashboard with it and the emergency lock.

Hands-on Experience & Implementation: We have implemented FIDO2/WebAuthn Level 2 passwordless authentication flows using @simplewebauthn/server (Node.js) and @simplewebauthn/browser for high-security enterprise and financial portals (e.g. LB Finance PLC disclosures: lbfinance.com ↗).

Admin Dashboard Protection Architecture:

  • Registration Ceremony: The server generates a cryptographically secure random challenge (32 bytes), storing it in a Redis cache with a 60-second TTL. The client invokes navigator.credentials.create() targeting physical authenticator attachments (authenticatorAttachment: 'cross-platform' for YubiKey 5 Series / SoloKeys). The server verifies the attestation statement, extracts the public key and credential ID, and stores them in PostgreSQL.
  • Authentication Ceremony: Case handlers tap their physical key via USB/NFC (navigator.credentials.get()). The server validates the cryptographic signature against the stored public key, checks the monotonic signature counter to detect cloned keys, and issues short-lived, encrypted, HttpOnly/SameSite=Strict session JWTs.
  • Emergency Lock ("Panic Button") Implementation: Triggered via a high-priority dashboard button or duress emergency code. The event immediately executes:
    1) Session Invalidation: Redis DEL user:sessions:* instantly revokes all active tokens across all devices in < 200 ms.
    2) Cryptographic Memory Wipe: The client and server wipe all ephemeral decryption keys from RAM using sodium_memzero().
    3) Decoy Screen & Database Freeze: Displays an innocent benign maintenance notice while locking database decryption behind multi-signature M-of-N trustee re-authorization.

SECTION 04 · OFFLINE SYNC & TENDER AGREEMENT
Unstable Networks · Conflict Resolution · Tender Exclusivity

Answers to Question 3 & Official Tender Commitments

Architecture for offline-first encrypted storage and deferred synchronization on intermittent Beninese cellular networks, followed by our formal agreement to all bid conditions.

QUESTION 3 How would you design offline-first storage and deferred sync for encrypted reports on unstable mobile networks (conflicts, retries, local protection)?

To guarantee zero data loss and absolute informant protection across unstable rural cellular networks (2G/3G in Benin), we design a 4-tier resilient pipeline:

  • 1. Client-Side Metadata Scrubbing Before Caching: The instant an image or video is captured, an Android native background service (or Web OffscreenCanvas + WebAssembly) strips all EXIF metadata, GPS latitude/longitude, timestamp tags, and camera serial numbers prior to touching local storage.
  • 2. Local Encrypted Storage (Data-at-Rest): On Android, reports and metadata-stripped media are written into SQLCipher (256-bit AES encrypted SQLite database) or WatermelonDB. The encryption key is derived using Argon2id and safeguarded in the hardware-backed Android KeyStore / StrongBox. If the physical phone is confiscated, raw files cannot be extracted without the hardware-backed key.
  • 3. Conflict-Free & Idempotent Deferred Sync: Because reports are append-only submissions, synchronization is naturally conflict-free. Each offline report receives a cryptographically random UUIDv4 and an SHA-256 idempotency hash generated from the encrypted payload. When the network reconnects, Android WorkManager triggers deferred synchronization with exponential backoff and network constraints (NetworkType.CONNECTED). If a connection drops mid-upload and retries, the server uses the idempotency token to avoid duplicate entries without reading plaintext.
  • 4. Panic Wipe & Zero-Trace Cleansing: Once the server acknowledges successful encrypted receipt, the local encrypted record is securely overwritten and purged using cryptographic shredding (random byte overwrite before file unlink).

FIDO2 Hardware Security & Emergency Lockdown

How the Case Dashboard is guarded by physical FIDO2 cryptographic tokens, backed by an instant-trigger Emergency Lock mechanism that purges active sessions and freezes local databases in under 200 milliseconds.

1. FIDO2 / WebAuthn Hardware Protection

Enforces hardware security keys (e.g., YubiKey 5 NFC, SoloKeys) as the mandatory authenticator.

• Origin-Bound Challenge: Signatures tied to domain, completely thwarting adversary reverse-proxies (Evilginx).
• Cloned Key Detection: Validates monotonic hardware signature counters on every ceremony.
• Passwordless Option: User presence (touch) + user verification (hardware PIN) satisfies NIST AAL3.
2. Emergency Lock Engine (< 200 ms)

Designed for high-threat scenarios where field offices or investigative hardware face immediate physical seizure.

• Session Purge: Invalidate all active Redis tokens across all dashboard sessions in under 200ms.
• RAM Key Erasure: Zeroes volatile decryption keys via sodium_memzero().
• M-of-N Recovery: Requires 2 of 3 offline trustee hardware tokens to restore database access.
