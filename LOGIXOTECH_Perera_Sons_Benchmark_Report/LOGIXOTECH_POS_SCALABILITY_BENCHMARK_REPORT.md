## 3. Project Background: Centralized POS Platform

A modern centralized POS platform for a multi-outlet enterprise serves several mission-critical functions:
* **Sales Transaction Processing:** Real-time recording of customer receipts, payment splits, discounts, and tax computations.
* **Terminal Communication:** Sub-second sync between floor POS hardware, kitchen display units (KDUs), and central servers.
* **Catalog & Pricing Distribution:** Immediate propagation of menu items, recipe variants, combo pricing, and seasonal promotions.
* **Inventory Depletion Tracking:** Real-time deduction of raw materials and finished goods to maintain operational visibility.
* **Centralized Business Reporting:** Management dashboards tracking hourly sales velocity, cash drawer balances, and branch performance.

### Performance Observations Following Feature Introduction:
* **Increased Query Activity:** Unindexed search queries generated by new reporting and status widgets.
* **Connection Exhaustion:** Surging terminal connection requests exhausting available database worker processes.
* **Row Lock Waits:** Multiple terminals updating common inventory or daily register summary rows concurrently.
* **API Latency Cascades:** Slower database responses holding backend API threads open, exhausting HTTP connection pools.

## 4. LOGIXOTECH Technical Engagement Workstreams

LOGIXOTECH organized the performance engagement into four rigorous engineering streams:

### A. Database Performance Investigation
* **Slow Query Profiling:** Leveraged `pg_stat_statements` to measure query execution frequency, total elapsed execution time, and buffer cache misses.
* **Execution Plan Deconstruction:** Executed `EXPLAIN ANALYZE` on critical sales recording and receipt queries, uncovering unindexed sequential table scans.
* **Resource Consumption Audit:** Identified database CPU spikes reaching 85%+ during meal peaks due to repeated sorting and in-memory hash joins.
* **Connection Starvation:** Identified unpooled client connections where each terminal spawned direct backend connections, hitting server connection caps.

### B. API and Application Performance
* **N+1 Query Cascades:** Identified order retrieval endpoints fetching parent order headers and then triggering individual queries for each line item.
* **Unthrottled Polling Loops:** Storefront terminals executed unthrottled polling intervals every few seconds to refresh menu status, saturating bandwidth.
* **Over-Fetching Payloads:** Endpoints retrieved full relational entity graphs with dozens of unneeded columns, inflating JSON serialization times.
* **Synchronous Blocking Tasks:** Long-running inventory and receipt email tasks were executed within the primary request-response thread.

### C. Transaction and Concurrency Investigation
* **Row Lock Contention:** Multiple terminals updating central inventory counts or daily register summaries experienced prolonged row-level lock waits.
* **Deadlock Risks:** Inconsistent acquisition ordering across `orders` and `order_items` tables caused occasional transaction rollbacks.
* **Duplicate Transaction Risks:** Lack of client-side idempotency keys meant cashiers re-submitted pending orders when network latency spiked.
* **Isolation Level Verification:** Evaluated Read Committed vs Repeatable Read tradeoffs to balance dirty read prevention against serialization errors.

### D. Verified Optimization Approaches
* **Composite & Partial Indexing:** Created targeted B-tree indexes on `(outlet_id, created_at)` and partial indexes for open active orders (e.g. `WHERE status = 'pending'`).
* **Connection Pool Architecture:** Implemented transaction-mode connection pooling (PgBouncer), capping backend processes while serving hundreds of terminals.
* **Batch Insertions & CTEs:** Replaced multi-roundtrip row inserts with single atomic Common Table Expression (CTE) write queries.
* **Idempotent Order Ingestion:** Enforced unique client-generated UUID keys to guarantee zero duplicate charges during network reconnects.

## 8. Database Integrity and Reliability Mechanisms

* **Duplicate Order Prevention & Idempotency:** Client-generated UUID keys prevent duplicate charges during cellular network dropouts.
* **Atomic Inventory Commits:** Stock deduction and sales transaction executed in a single atomic transaction block.
* **Lock Mitigation Protocols:** Utilizing `FOR UPDATE SKIP LOCKED` and short-lived advisory locks to prevent queuing bottlenecks.
* **Deterministic Locking Order:** Sorting line item updates across transactions to physically eliminate cross-table deadlocks.

## 9. Direct Technical Relevance to the YouZen Platform

The architectural lessons from multi-outlet POS optimization map directly to the requirements of the **YouZen platform (100 restaurants and 100 hair salons on shared PostgreSQL/Supabase)**:

| YouZen Operational Area | Concurrency & Database Challenge | LOGIXOTECH Engineering Approach |
| :--- | :--- | :--- |
| **Restaurant Checkout Rush** (100 POS + 200 phones) | Simultaneous meal-time checkouts, table bill splits, and kitchen ticket dispatch creating hot-row lock queues on `orders`. | Composite indexes on `(location_id, status)`, atomic CTE order ingestion, and PgBouncer connection multiplexing. |
| **Hair Salon Bookings** (Calendars & availability) | Multi-user race conditions where concurrent online users and phone desks attempt to book the exact same stylist time slot. | PostgreSQL exclusion constraints (`EXCLUDE USING gist`) and range types (`tsrange`) to physically eliminate double-bookings. |
| **Supabase Realtime Traffic** (Live kitchen & calendar sync) | Hundreds of mobile staff devices listening to Postgres WAL changes, triggering connection exhaustion and redundant reads. | Scoping Realtime channel subscriptions strictly by `location_id` and implementing client-side debounced invalidation. |
| **Row-Level Security (RLS)** (Tenant data protection) | Multi-tenant RLS policies on shared tables re-evaluating subqueries on every single scanned row, spiking query latency. | Refactoring RLS policies to use session-cached JWT claims and `STABLE` security-definer helper functions. |
